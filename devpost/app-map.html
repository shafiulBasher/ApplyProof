ApplyProof App Map

A one-page guide to how ApplyProof works, where its pieces live, and where to start when you want to change something.

What it does

ApplyProof checks an applicant's real files against an official application guideline. Gemini reads only the guideline and lists its requirements, each with an exact quote; plain code confirms every quote and then measures your files (pages, words, document counts, eligibility details). Every finding shows its evidence, and anything the app can't confirm is Needs Verification, never a guess. Everything is stored in your browser.

Pages you seeLanding, dashboard, calendar, and each application, in app/ and components/.
Browser storageApplications, files, and results in IndexedDB, via lib/db.ts. Clearing browser data removes them.
Local helper routesapp/api/parse reads PDFs; app/api/extract asks Gemini about the guideline only.
The checkerPlain code in lib/checks.ts turns each requirement into a finding. No AI.

One action, end to end: “Run Readiness Check”

Code route reference route, not a completed tour

Open the project in your editor and use search (Ctrl+Shift+F in VS Code) for each anchor below.

  1. The button, app/applications/[id]/page.tsx, search async function run(). Clicking Run Readiness Check calls runCheck with the latest saved details and documents, then reloads the page data.
  2. Reuse or read the guideline, lib/runCheck.ts, search export async function getExtraction. If this exact guideline was read before, its saved requirements are reused, which is why reruns are instant and free. Otherwise only the guideline's page texts go to app/api/extract/route.ts (Gemini prompt: const PROMPT in lib/ai/gemini.ts), and code verifies every quote.
  3. The checker, lib/checks.ts, search export function runChecks. Each requirement becomes Passed, Action Needed, or Needs Verification by plain code. readEligibility re-reads GPA numbers or a degree level from the verified quote when the AI mislabels a rule. The results appear through components/ResultsPanel.tsx.

A practice to reuse

Let the AI propose, let code verify, and test the interpretation, not just the finding

What happened: the open question in planning was whether a free model reads requirements well enough. samples/expected-requirements.json and npm run test:extraction turned “good enough” into a test, and Gemini scored 10/10 with every quote verified. Real use still exposed interpretation errors the test didn't cover: a “3.0 on a 4.0 scale” rule labeled unclear, missing degree details, and EU work authorization filed as nationality.

What fixed it: plain code re-reads the verified quote instead of trusting the AI's label (readEligibility in lib/checks.ts), and each real failure got a test (search mislabeled by the AI and EU work authorization in tests/checks.test.ts).

Next time: write the expected output as a test before trusting an AI step, include varied real-world samples, check how results are interpreted as well as whether they're found, and add a test every time real use breaks an assumption.

Run it again

  1. npm install
  2. Copy .env.example to .env.local and add your free GEMINI_API_KEY
  3. npm run dev, then open http://localhost:3000
  4. Checks: npm test (unit tests), npm run test:extraction (live accuracy test, one free Gemini request)
Where the sample files are

samples/ has the fictional scholarship (guideline, 3-page and 2-page CVs, letters, transcript); samples/job/ has the fictional job posting (PDF and pasted-text versions) with a résumé, cover letter, and references.
